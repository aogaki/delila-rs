The problem

No trigger, so nothing throttles the rate

Listmode: every hit written out on its own, with its own timestamp; coincidences applied later, offline.

Design rule · non-negotiable

If the system cannot keep up, it stops. It does not throw data away.

  • Every ZeroMQ socket runs HWM = 0; internal channels are unbounded. No back-pressure path is permitted to drop.
  • One documented exception: hits still in flight when the run is stopped. They are counted in dropped_batches and logged — never silent. A non-zero count while running is a bug report, not a tuning knob.
Concurrency model

One task per stage, no shared locks

No mutex is ever held across a stage boundary, so a slow consumer cannot stall an unrelated producer. Decoding — the measured bottleneck — is fanned out over N workers behind a reorder buffer, so the number of workers never changes the output.

  • 66 k lines of Rust, 761 automated tests
  • unsafe confined to the CAEN FFI wrapper layer
  • No pattern-matching heuristics in the decoder hot path — every field traced to a firmware specification page and verified against hardware

Verification

Audited, not asserted

  • All 407 runs re-read from disk. 392 closed cleanly; the 15 killed mid-file were recovered by the block scanner — which is why the count above can be stated at all.
  • Event-builder output checked against an independent offline analysis of the same run — coincidence yields identical, event for event.
  • Order-inclusive hash identical for 1 and 4 worker threads — parallelism is not visible in the output.
  • End-of-stream markers carry their run number, so a late marker cannot truncate the following run.

Loss-free · run 0390

A 2 Hz heartbeat, 3.3 days long

The same campaign fans a pulser into every channel. That turns the claim into something countable: over 78.27 hours of continuous running — twelve digitizers, 208 channels, 10 991 102 925 events — the pulser should fire 559 017 times. Every one of them has to be in the file.

How it was built

Specified in prose, written by agents

Nearly all of this code was produced by AI agents working from written task documents — one per unit of work, each carrying the requirement, the decisions and their reasons, and the evidence of hardware verification. The prose is not documentation written afterwards. It is the input.

Availability

Run the whole chain with no digitizer attached.

Reader, merger, recorder, monitor and operator all come up against a built-in emulator, so the whole pipeline runs on any machine. Every ELIADE node is accepted this way — 10 300 events, zero trigger loss — before it is trusted with a detector.
